## 二、架构与硬约束

- **单进程、单 EGL Surface**：port 的 `OHOSForceRepaint` 已注明；内容进程（e10s）在 OHOS 无法启动（status 127）。
- **classic 轨道（geckoview.xhtml）**：没有浏览器 chrome（无 nsContextMenu/browser.xhtml），
  因此部分桌面浏览器能力需要我们在 geckoview.js 里自建（上下文菜单已如此处理）。
- **JIT 依赖 ACL**：已取得 `ALLOW_WRITABLE_CODE_MEMORY` + `DISABLE_CODE_MEMORY_PROTECTION`，
  `libxul.so` 注入 `.permission` 段；无 ACL 时只能解释器（坚盾降级）。
- **HSP 打包与安装**：`bm install -r` 不会替换未变版本的 HSP，改动 gecko 模块必须卸载重装。
- **体积**：HSP ≈ 292 MB（libxul 185 MB、omni.ja 65 MB、依赖库 ~42 MB）。

## 三、质量与风险

| 风险 | 说明 | 影响 |
|---|---|---|
| 无崩溃隔离 | 单进程，页面崩溃=应用崩溃 | 高 |
| 无崩溃上报 | 仅 hilog/faultlogger，无 minidump 收集 | 中 |
| 长稳未知 | 多标签/多次导航/内存增长尚未做连续压测 | 高 |
| 下载/文件选择 | 下载存沙箱、Picker 复制到 cache 未清理 | 中 |
| 菜单完整性 | 缺保存图片/查看源码/检查元素/新标签打开链接 | 中 |
| 体积 | 292MB，安装/分发成本高 | 中 |
| 工程化 | 改动多为脚本化 patch，缺 CI/回归 | 高 |

## 四、建议路线图（下一阶段）

### P2-1 稳定性与长稳（最高优先）
1. 连续压测脚本：N 轮「打开多个标签→导航→返回→切换→关闭」，记录内存/句柄/崩溃；
2. 崩溃上报：接入 `GeckoSignalHandler`/faultlogger 收集 minidump 或 crash json，落盘 + 提示；
3. 页面错误覆盖：DNS/证书/超时错误页统一（当前仅超时看门狗）；
4. 资源回收：标签关闭后的内存回落验证。

### P2-2 浏览器壳完善
1. 菜单补全：保存图片、在新标签打开链接（需 ArkTS 侧建标签的跨层通道）、查看源码/检查元素（可选）；
2. 下载管理：另存为/打开文件/清理缓存；
3. 历史/书签与引擎 URL 双向同步、地址栏自动补全；
4. 深色模式、页面缩放记忆、阅读模式（可选）。

### P2-3 体积与性能
1. HSP 目标 ≤ 200MB：按需裁剪 libxul（`--disable-*`）、分离调试符号、omni 压缩策略、依赖库 strip；
2. 启动优化：延迟加载非首屏模块、profile 预热、预连接；
3. JIT 调优：Ion/Warp 预热阈值、WASM 路径验证。

### P3 工程化
1. CI（Linux 交叉构建 + 可选真机冒烟），产物版本化；
2. 把 scripts 下的增量 patch 收敛为一份干净工程快照；
3. 回归清单自动化：启动/页面/输入/IME/标签/菜单/JIT 开关。

### P4 合规与分发
1. Firefox 商标/Logo 不可直接用于第三方发行；MPL-2.0 声明与源码获取方式；
2. 第三方库许可清单（NSS/NSPR/libvpx/ffmpeg 等）；
3. ACL 已有；如上架需按应用市场要求提交权限场景说明。

## 五、结论

引擎侧（渲染/JIT/网络/多标签）与基础交互已经可用，项目重心应从"能不能跑"转向
**"稳定、好用、可维护、可分发"**：先做长稳与崩溃上报，再补壳层完整度，最后做体积与工程化。
"native(browser.xhtml) 轨道"可作为探索项（能直接获得完整 chrome UI，但迁移成本高），
不建议作为近期主线。
